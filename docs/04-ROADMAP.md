# 04 — Implementation Roadmap and Risks

## Verification: what this environment can and cannot prove

Read this before the phase list; it is why the phases are ordered the way they are.

**What CI can prove:**

* The project **compiles** (`./gradlew assembleDebug`).
* **JVM unit tests pass** (`./gradlew test`, `app/src/test/`).
* Lint/static checks pass.

**What nothing here can prove:**

* That the app **runs**. There is no Android SDK on the dev machine and **no emulator in CI**.
  No screen has ever been rendered by this project and none will be until a human installs the
  APK on a real device.
* That anything **talks to a host**. There is no Sunshine, Apollo, or GFE machine reachable
  from this environment, and there never will be during development.
* That instrumented tests (`androidTest`) or Compose screenshot tests pass — they need a device.

**Consequences, which are binding:**

1. **Every phase gate is labelled `[CI]` or `[USER]`.** A `[CI]` gate is a command that either
   passes or fails here. A `[USER]` gate can only be checked by a person with a device and a
   PC, and is written as an instruction to that person — not as a task we can tick off.
2. **No phase may be blocked on a `[USER]` gate.** Work continues; the gate is recorded as
   outstanding. Otherwise the project stops at Phase 5 forever.
3. **`[USER]` gates accumulate into a checklist** (§Outstanding user verification) that ships
   with the build. It is the honest statement of what has never been observed to work.
4. **No test may depend on a capture from a real host.** Fixtures are hand-written from the
   byte layouts in `01-PROTOCOL.md`, or generated by our own encoder. A test that needs a PC is
   not a test, it is a wish.

**Ordering principle:** every phase ends with the project **compiling and its unit tests
green**. Where a phase depends on something not yet built, it depends on an *interface* with an
honest stub — one that logs and returns a failure, never one that pretends.

**Second principle, revised for this environment:** get to a **visually complete, installable
APK** as early as possible, because visual fidelity is the half of this product that can
actually be reviewed without a PC. Protocol work then lands behind stubs that the UI already
consumes. Milestone **M1** below is that APK; everything host-dependent sits behind it.

## Phase 4 — Protocol foundations (pure JVM, fully testable here)

Everything in this phase is byte manipulation with no I/O, which makes it the most thoroughly
verifiable work in the project. Do it properly.

* `ProtocolConstants.kt` — **every** port, magic, flag, and timeout from `01-PROTOCOL.md`,
  cross-referenced by spec section in comments. Nothing else may define a protocol constant.
* `ByteIO.kt` — explicit LE/BE readers/writers plus `netfloat` helpers.
* `InputPackets.kt` — every packet builder from `01-PROTOCOL.md` §10.3.
* `ButtonFlags.kt`, `KeyCodeMap.kt`.
* `XmlResponse` / `ServerInfo` / applist parsing.
* `SdpBuilder` / `SdpParser`.
* `PairingCrypto` — `saltPin`, zero-padded AES-128-ECB, hash selection.
* `ControlMessageTypes` tables.

**Gate `[CI]` — the strongest gate in the roadmap, and all of it runs here:**
1. Hex-fixture round-trip test for **every** packet builder; fixtures written by hand from the
   spec's byte layouts.
2. `PairingCrypto` known-answer tests: fixed salt + PIN ⇒ fixed AES key; fixed inputs ⇒ fixed
   SHA-1 and SHA-256 digests.
3. `SdpBuilder` golden-file test for three configurations (1080p60 H.264 stereo; 4K60 HEVC HDR;
   1080p120 AV1) — asserts our output, not the host's acceptance of it.
4. XML parsing against hand-written fixtures including a truncated document and a
   non-200 `status_code`.

## Phase 7 — Video: receive, reassemble, decode

* `UdpSocketFactory` (1 MB+ receive buffers, buffer pooling).
* `VideoReceiver` + 500 ms ping thread (legacy and `X-SS-Ping-Payload` variants).
* `RtpParser`, `NvVideoPacket`, `FrameAssembler` — **without** Reed-Solomon: a frame completes
  only when all data shards arrive; on loss, drop and request an IDR.
* `DecoderProbe`, `MediaCodecVideoDecoder` (async, dedicated `HandlerThread`, three-tier
  low-latency configure fallback, immediate `releaseOutputBuffer(index, true)`).
* Bounded decode queue (capacity 2, drop-oldest + IDR).

**Reed-Solomon is deliberately deferred to Phase 11.**

**Gate `[CI]`:** `FrameAssembler` synthetic-sequence tests — in-order, reordered, single loss,
block loss, multi-FEC-block — asserting the **exact bytes** of the reassembled frame. These
need no host: the packets are generated from the spec's layout.
**Gate `[USER]`:** a live game renders on the device. Measure the gap between "frame
reassembled" and "frame rendered"; more than ~2 frame intervals means the decoder is queueing
(Risk 4).

## Phase 8 — Control stream and input

The phase most likely to slip. Budget accordingly.

* `EnetHost`/`EnetPeer`/`EnetChannel`: connect handshake with connect data, reliable ordered
  channels, ACKs, retransmit, fragmentation, ping/timeout.
* `ControlStream`: Start A/B, periodic ping (`0x0200`, reliable, 500 ms), inbound dispatch,
  termination with error-code mapping, rate-limited IDR requests.
* `InputCrypto` with the pluggable IV strategy (documented default + counter fallback behind a
  debug setting).
* `InputSender` batching, all-reliable sending.
* `ControllerManager`/`ControllerMapper`: hotplug, axis mapping, dead zones, Y inversion,
  arrival/removal, `SS_CONTROLLER_ARRIVAL` with the `emulatedControllerType` policy
  (`02-ARCHITECTURE.md` §6.2).
* `MotionSensors` (rate-limited, unit-converted), `RumbleSink`.
* Point Phase 3's logging `InputSink` at the real sender — no UI changes.

**Gate `[CI]`:** the ENet **loopback test** — two instances over `127.0.0.1` with injected loss
and reordering, asserting reliable ordered delivery and fragment reassembly. This runs here and
must pass before anyone points it at a host.
**Gate `[USER]`:**
1. Mouse movement visibly moves the host cursor (validates IV chaining — Risk 2).
2. A clean disconnect leaves the host reporting `SUNSHINE_SERVER_FREE`, not a stuck session.
3. No stuck buttons after backgrounding the app mid-input.

## Phase 10 — Session capture and replay *(debug tooling)*

* A debug-only recorder that writes every received UDP payload, with arrival timestamps, to a
  file; and a replayer that feeds those files back into `VideoReceiver`/`AudioReceiver` as if
  they came from a socket.

**Why it is its own phase:** it converts a single session on someone's real PC into a permanent,
CI-runnable regression fixture. The first person to run Phase 7 successfully should capture
one and commit it. Until then the replayer is exercised by **synthetic** captures generated
from our own packet builders — which is enough to prove the tooling itself works.

**Gate `[CI]`:** a synthetic capture round-trips through recorder and replayer with byte
equality.

## Phase 11 — Reed-Solomon FEC

* `ReedSolomon` over GF(2^8), `encode` / `decode(shards, marks)`.
* Wire into `FrameAssembler` and `AudioFecBlock` behind a flag defaulting to on, with a kill
  switch.
* Sunshine per-frame FEC status reporting (`0x5502`).

**Gate `[CI]` — non-circular, and this is the fix:** the earlier plan validated FEC by
replaying a capture that only a real host could produce, which cannot run here. Instead:

1. **Self-consistency:** our own `encode` produces `parityShards` from `dataShards`; for every
   subset of ≥ `dataShards` surviving shards, `decode` reconstructs the originals **byte for
   byte**. Exhaustive for small blocks, randomized for large ones. This proves the
   implementation is a correct erasure code.
2. **Known-answer vectors:** a small set of `(dataShards, parityShards, input, expected parity)`
   triples committed as fixtures, computed independently from the GF(2^8) field arithmetic
   defined in the test itself (log/antilog tables built from the primitive polynomial). This
   proves the implementation matches *a specific, documented* matrix construction rather than
   merely being self-consistent — the only part that interoperability actually depends on.
3. **Wiring:** `FrameAssembler` recovers a frame when parity shards substitute for dropped data
   shards, asserted against the synthetic sequences from Phase 7.

What CI **cannot** prove is that the host uses the same matrix (Risk 1). That is a `[USER]`
gate, and if it fails the kill switch returns us to the Phase 7 drop-and-IDR behaviour.

**Gate `[USER]`:** on a lossy Wi-Fi link, recovered frames decode cleanly rather than showing
corruption. **If frames are corrupt where they were previously merely dropped, turn FEC off** —
that is Risk 1 landing, not a decoder bug.

## Risk register

Ordered by expected pain. For each: what breaks, how we know early, and what we do about it.

### 1. Reed-Solomon interoperability — **highest**

*The risk:* GF(2^8) Reed-Solomon has multiple incompatible matrix constructions. If ours
differs from the host's, recovery silently produces corrupt frames — which is *worse* than no
recovery, because corrupt frames look like decoder bugs and will send us hunting in the wrong
place for days.

*Early signal:* the Phase 11 known-answer vectors disagree with our matrix, or `[USER]` gate U8
reports corrupt recovered frames while all-shards-present frames are fine.

*Mitigation:* already structural — FEC recovery is **not on the critical path**. Phase 7 ships
without it. Phase 11 is additive and killable. Never enable recovery without the Phase 11 `[CI]`
self-consistency and known-answer gates passing first. Note what CI cannot settle: those gates
prove we implement *a* correct erasure code with *a specific documented* matrix — they cannot
prove the host uses the same one. That remains U8.

*Honest expectation:* **this may not fully work in v1.** LAN streaming with drop-and-IDR is
acceptable; congested Wi-Fi will be noticeably worse than Moonlight until this lands.

### 2. Input encryption IV chaining — **highest**

*The risk:* the AES-GCM IV derivation and per-message chaining rule (spec 01 §10.1) is the
least-documented part of the protocol, and Java's 12-byte GCM IV requirement forces a
truncation choice that is also unverified. Get it wrong and **the host silently discards every
input packet** — no error, no log, just a game that ignores you.

*Early signal:* Phase 8 `[USER]` gate #1 (U6). Move the touchpad; if the cursor does not move
but video and control pings are healthy, this is the cause. **No CI test can catch this** — the
packet bytes are asserted in Phase 4 and will look perfectly correct.

*Mitigation:* the IV strategy is an interface with at least two implementations (chained
ciphertext-tail, and incrementing counter) selectable from a debug setting, plus a hex log of
the first three input packets. Debugging this against Sunshine's own logs (Sunshine logs
decrypt failures) is the fastest route.

*Honest expectation:* costs a day, not a week, **if** the strategy is pluggable from the start.
If it is hardcoded, it costs a week.

### 3. Writing ENet from scratch — **high**

*The risk:* ENet is a real reliable-UDP protocol with sequencing, ACK batching, retransmit
timers, fragmentation, MTU discovery, and a connect handshake. Reimplementing "enough of it" is
a classic underestimate. A subtly wrong retransmit timer produces input lag that only shows up
under loss.

*Early signal:* the Phase 8 `[CI]` loopback test — if it takes more than two days to make two of
our own instances talk reliably under simulated loss, the real host will be worse. This is one
of the few high-risk areas CI genuinely covers, so the signal arrives early and cheaply.

*Mitigation:* implement the **minimum viable subset**: connect, reliable-ordered on two
channels, fragmentation, disconnect. Skip bandwidth throttling, unsequenced delivery, and
compression entirely. Test on loopback before touching a host. Keep the send path
single-threaded.

*Escape hatch:* if this stalls the project, the licensing-clean option is to bind the upstream
C library via the NDK. That contradicts our "no native code" posture in `00-OVERVIEW.md` §4 and
must be a deliberate, discussed decision — not a quiet Friday-afternoon fix.

### 4. MediaCodec low-latency behaviour across vendors — **high**

*The risk:* the standard `KEY_LOW_LATENCY` is API 30+ and inconsistently honoured; the vendor
keys are undocumented and differ per SoC; some codecs throw on `configure()` when given a key
they dislike; some buffer 3–4 frames regardless of what we ask, which destroys the value
proposition.

*Early signal:* Phase 7 `[USER]` gate (U5) on a real device — measure the delta between "frame
fully reassembled" and "frame rendered". More than ~2 frame intervals means the codec is
queueing. Unreachable from CI: no emulator has a hardware decoder.

*Mitigation:* the three-tier configure fallback (all keys → standard keys → none), never
letting a vendor key block streaming; per-device logging of which keys were accepted; a
device-quirks table we populate from real logs.

*Honest expectation:* latency will vary meaningfully by device and we will not be able to fix
the worst offenders. Set expectations rather than chasing them.

### 5. GFE (NVIDIA) hosts are largely untestable — **medium**

*The risk:* GameStream is discontinued. We carry Gen 3/4/5 code paths and NVIDIA-specific
workarounds (SOPS clamping, the `fps=0` hack, no Native Touch, no controller-arrival packets)
that we probably cannot test against real hardware.

*Mitigation:* implement them from the spec, gate them behind `isNvidiaGfe`, and **log loudly**
when a GFE path executes. Do not let untestable GFE code complicate the Sunshine path — where
they diverge, branch early and keep the branches separate.

*Honest expectation:* **GFE support is best-effort and may be broken at ship.** Say so in the
release notes rather than implying parity.

### 6. Surround audio — **medium, and already scoped out**

*The risk:* Android's `MediaCodec` Opus decoder does not reliably handle multistream
(mapping family 1) surround. The channel-order fix-up (spec 01 §8.3) adds a second place to be
wrong.

*Mitigation:* v1 is stereo-only with the surround options visibly disabled and explained. The
fix is a bundled libopus, which is a Phase 13 item and needs a frozen-catalog exception
(`00-OVERVIEW.md` §4.12).

*Honest expectation:* **5.1/7.1 will not work in v1.** This is a deliberate, documented gap,
not a bug.

### 7. mDNS discovery reliability — **medium**

*The risk:* `NsdManager` is genuinely flaky: serialized resolution on older APIs, silent
failures behind VPNs, routers with client isolation, ROMs that need a multicast lock.

*Mitigation:* manual IP entry is a first-class feature, not a fallback; the empty state names
the likely cause; saved hosts are polled directly by IP and do not depend on discovery at all
after the first sighting.

*Honest expectation:* some users will always have to add hosts manually. Design for it.

### 8. Foreground-service and background-execution policy — **medium**

*The risk:* API 34 tightens foreground-service types; OEM battery managers kill long-running
services aggressively; a killed service mid-stream leaves a stuck session on the host.

*Mitigation:* correct `mediaPlayback` type + runtime permission; the service owns the session
so Activity churn is harmless; the host's own session timeout is the backstop. Test on at
least one Xiaomi/Samsung device, where the policies are harshest.

### 9. HDR correctness — **medium-low**

*The risk:* HDR that "works" but looks washed out or over-saturated is common and hard to
diagnose. Metadata plumbing (`KEY_HDR_STATIC_INFO`, transfer function, the mid-stream HDR
control message whose layout is unverified) has several failure points that all look the same
on screen.

*Mitigation:* Phase 12, after everything else is stable. Log the codec's actual output format.
Ship with HDR **off by default**.

### 10. Codec/host capability negotiation guesswork — **low-medium**

*The risk:* `ServerCodecModeSupport`'s bit assignments are unverified (spec 01 §3.3.1); we may
offer a codec the host cannot encode.

*Mitigation:* the failure mode is clean — ANNOUNCE returns a non-200 and we surface it.
Use the reliable `MaxLumaPixelsHEVC == 0` check for HEVC, treat the bitfield as a hint, and log
the raw value from every host so the table can be corrected from real data.

### 11. Scope creep in the on-screen controls — **low, but insidious**

*The risk:* the reference's on-screen widget system is enormous (custom layouts, profiles,
duplicate/delete, visual feedback). It is easy to spend the whole project there.

*Mitigation:* v1 ships **two fixed presets** built on a data-driven layout model. "Custom" is
visibly disabled with an honest explanation. The editor is Phase 13 and the data model already
supports it, so deferring costs nothing structurally.

### 12. Byte-order and struct-packing bugs — **certain, but cheap if caught early**

*The risk:* not a matter of *if*. The protocol mixes LE and BE within a single packet
(spec 01 §0.1), and a wrong-endian field usually manifests as a completely dead subsystem
rather than a subtle glitch.

*Mitigation:* the non-negotiable rule from `02-ARCHITECTURE.md` §10 — every packet builder gets
a hex-fixture round-trip unit test written **at the same time as** the builder. This is the
single highest-value testing investment in the project, and — unlike most of this list — it is
fully covered by `[CI]`.

### 13. Verification blindness — **structural, and it colours everything above**

*The risk:* this project is being built without ever running. No emulator, no device, no host.
Compilation and JVM unit tests are the entire feedback loop. Whole categories of defect —
layout that clips, a decoder that stalls, a socket that never binds, a service the OEM kills,
input the host silently drops — are invisible here **by construction**, and the first person to
install the APK will find a batch of them at once.

*Early signal:* there isn't one. That is the risk.

*Mitigation:* (a) push everything provable into JVM tests, which is why Phase 4 front-loads all
byte-level work and why Phase 3 makes gesture and coordinate maths unit-testable rather than
burying it in composables; (b) reach an installable, visually complete APK at **M1** so human
review starts early on the half that can be reviewed at all; (c) label every gate `[CI]` or
`[USER]` so nobody mistakes "the tests pass" for "it works"; (d) keep the
§Outstanding user verification list current and ship it with the build.

*Honest expectation:* **"CI is green" means "it compiles and the maths is right", nothing
more.** Do not describe an unverified phase as done — describe it as written and untested.

## Summary of what is honestly likely to be incomplete at v1

1. **Reed-Solomon FEC recovery** — may be absent or disabled; degrades quality under loss.
2. **Surround audio (5.1 / 7.1)** — deliberately not shipped; stereo only.
3. **NVIDIA GFE hosts** — implemented from spec, likely untested, possibly broken.
4. **Custom on-screen control layouts** — presets only.
5. **External display / presentation mode** — not implemented.
6. **Automatic reconnect after a drop** — manual resume only.
7. **HDR** — implemented but off by default and expected to need device-specific fixes.
8. **AV1** — negotiated where probed, but hardware decode quality varies wildly.
9. **Encrypted control/video/audio streams (Sunshine)** — negotiated as off.
10. **ENet edge cases** — fragmentation and heavy-loss behaviour will be the least-exercised

11. **Settings favorites** — designed (`03-UI-SPEC.md` §4.10) but not built; the overflow menu
    omits the entry until it is.
12. **Everything past Phase 3, in the sense that matters most** — written and unit-tested, but
    never observed working, because this environment cannot observe it (Risk 13). The
    §Outstanding user verification table is the real status of the product.
